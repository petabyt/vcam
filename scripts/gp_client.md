# Testing vcam with libgphoto2 over the fake libusb shim

The `usb-vcam` build target (`build/libusb-vcam.so`) is a drop-in libusb-1.0
replacement. When a client process is started with it preloaded, the camera
runs *inside the client process* and libusb calls are answered by
`src/usb/libusb.c`.

`libgphoto2`'s `ptp2` camlib is the reference PTP client; its USB port backend
(`libgphoto2_port/libusb1/libusb1.c`) drives the shim, so gphoto2 behaves as if
a real camera were plugged in.

## Models

`canon_1300d` uses a hand-written registration superset. The dump-derived
models are generated by `scripts/eos_dump2c.py` from libgphoto2's camera dumps
(`camlibs/ptp2/cameras/*.txt`) into `src/canon/models/`, registering each
camera's advertised vendor ops and its device properties with the exact value
widths the client expects:

| CLI tag | Model | USB PID |
|---------|-------|---------|
| `canon_1300d` | Canon EOS Rebel T6 | 0x32b4 |
| `canon_5d3` | Canon EOS 5D Mark III | 0x323a |
| `canon_90d` | Canon EOS 90D | 0x32ea |
| `canon_200d` | Canon EOS Rebel SL2 | 0x32cc |
| `canon_r` | Canon EOS R | 0x32da |
| `canon_g7x3` | Canon PowerShot G7 X Mark III | 0x32f0 |

Regenerate after dumps change:

```sh
D=/path/to/libgphoto2/camlibs/ptp2/cameras
scripts/eos_dump2c.py $D/canon-eos5dmark3.txt 5d3 $D/canon-eos90d.txt 90d \
	$D/canon-eos200d.txt 200d $D/canon-eos-r.txt r \
	$D/canon-powershot-g7x-markiii.txt g7x3
```

Properties skipped by the generator: string-typed codes (Owner, Artist,
Copyright, SerialNumber, LensName, CameraNickname, CustomFuncEx, FocusInfoEx),
packed ImageFormat* codes and CustomFunc1-11 - the client hardcodes their
parsing and would misinterpret simple values. Dumps without an event section
(e.g. G7 X Mark III) get only the capture-critical properties from
`canon_ensure_capture_props()`.

## Nikon models

The Nikon implementation (`src/nikon/`) emulates the standard Nikon vendor
protocol as understood by gphoto2's ptp2 camlib: `VendorExtensionID 0xa`,
`GetVendorPropCodes` (0x90CA) / `GetVendorCodes` (0x9439, Z-series) during
init, event polling through `GetEvent` (0x90C7) / `GetEventEx` (0x941C),
`InitiateCaptureRecInMedia` (0x9207) captures to SDRAM (handle 0xffff0001,
announced with 0xC101/0xC102 events) or to the card (/DCIM/100NIKON,
announced with ObjectAdded/CaptureComplete), live view (0x9201/02/03) and
`DeviceReady` (0x90C8) for the wait-busy loop.

| CLI tag | Model | USB PID | Notes |
|---------|-------|---------|-------|
| `nikon_d7500` | Nikon DSC D7500 | 0x0440 | 238 device properties |
| `nikon_z6_2` | Nikon Z6_2 | 0x044c | 278 device properties + 0x9439 |

The per-model property tables in `src/nikon/models/` are transcribed from
libgphoto2's camera dumps (`camlibs/ptp2/cameras/nikon-*.txt`, "Device
Property Summary" section) with the exact data types, forms and values a
real body reports - `gphoto2 --summary` against the emulator is
byte-identical to the dumps. Events are queued on a dedicated channel and
served by both the GetEvent/GetEventEx opcodes and the USB interrupt
endpoint (first consumer wins, like on real hardware).

gphoto2's `ptp2/autofocus` and `ptp2/capturetarget` settings (from
`~/.config/gphoto/settings`, written by `--set-config capturetarget`)
select the 0x9207 capture parameters; with no settings file gphoto2 sends
no-AF + SDRAM. The "Capture Target" widget choices are "Internal RAM"
(sdram) and "Memory card" (card).

## Sony models

The Sony implementation (`src/sony/`) emulates the Sony SDIO remote-control
protocol ("mode 3", For 2020 Models or Later) as understood by gphoto2's
ptp2 camlib: `VendorExtensionID 0x11`, the init handshake
`SDIO_Connect` (0x9201, phases 1/2/3) + `SDIO_GetExtDeviceInfo` (0x9202,
protocol 0x12c = mode 3, response carries the vendor property and control
code lists), property cache refills through
`SDIO_GetAllExtDevicePropInfo` (0x9209, packed Sony DPD records served
live), property writes via `SDIO_SetExtDevicePropValue` (0x9205) and the
shutter driven through `SDIO_ControlDevice` (0x9207): 0xD2C1
ShutterHalfRelease / 0xD2C2 ShutterRelease, u16 2 = press, 1 = release.
Capture lands in SDRAM at handle 0xffffc001, live view JPEG at 0xffffc002
(4-byte LE offset to the SOI), both gated by 0xD215 ObjectInMemory
(0x8001 = one image ready; fetching the object clears it, which is what
gphoto2's stale-image cleanup loop expects). Events go over the classic
USB interrupt endpoint: 0xC203 DevicePropChanged (param = propcode, also
used to signal 0xD213 FocusFound) and 0xC201 ObjectAdded
(param = handle). There is no GetEvent-style polling opcode for Sony.

| CLI tag | Model | USB PID | Notes |
|---------|-------|---------|-------|
| `sony_a7m4` | Sony ILCE-7M4 | 0x0da7 | 26 device properties, mode 3 |
| `sony_a7r5` | Sony ILCE-7RM5 | 0x0e0c | 27 device properties, mode 3 |

The per-model property tables in `src/sony/models/` are transcribed from
libgphoto2's camera dumps (`camlibs/ptp2/cameras/sony-*.txt`, "Device
Property Summary" section = the real bodies' 0x9209 stream) with the exact
data types, forms and values a real body reports - including Sony's
quirks: many properties ship with empty enumerations, Capture Formats is
empty, PC-control bodies report no storages, and the 0xD2Cx controls
(shutter/buttons) are listed in DeviceInfo but never answered by 0x9209
(gphoto2 synthesizes their descriptors client-side). Standard PTP
properties (FNumber, FocusMode, StillCaptureMode, ...) are served through
the 0x9209 cache as well, since gphoto2 routes all Sony property reads
there.

Note: gphoto2's "Capture Target" widget row carries no datatype, so
`--set-config capturetarget` sends an empty 0x9205 data phase even against
real bodies; the Sony capture flow always pulls from SDRAM regardless.
Shutter speed (`--set-config shutterspeed=1/250`) exercises the real u32
write path - gphoto2 caches property descriptors for 2 seconds, so a read
back needs `--wait-event=4s` in between.

Test with `scripts/regression-sony-gp.sh`, or manually:

```sh
LD_PRELOAD=build/libusb-vcam.so VCAM_USB_MODEL=sony_a7m4 \
	gphoto2 --auto-detect
LD_PRELOAD=build/libusb-vcam.so VCAM_USB_MODEL=sony_a7m4 \
	gphoto2 --capture-image-and-download --force-overwrite
LD_PRELOAD=build/libusb-vcam.so VCAM_USB_MODEL=sony_a7m4 \
	gphoto2 --capture-preview --force-overwrite
LD_PRELOAD=build/libusb-vcam.so VCAM_USB_MODEL=sony_a7m4 \
	gphoto2 --trigger-capture --wait-event-and-download=FILE --force-overwrite
LD_PRELOAD=build/libusb-vcam.so VCAM_USB_MODEL=sony_a7m4 \
	gphoto2 --set-config shutterspeed=1/250 --wait-event=4s --get-config shutterspeed
```

Test with `scripts/regression-nikon-gp.sh`, or manually:

```sh
LD_PRELOAD=build/libusb-vcam.so VCAM_USB_MODEL=nikon_d7500 \
	gphoto2 --auto-detect
LD_PRELOAD=build/libusb-vcam.so VCAM_USB_MODEL=nikon_d7500 \
	gphoto2 --capture-image-and-download --force-overwrite

	gphoto2 --capture-preview --force-overwrite
```

## Model selection

By default the shim exposes `canon_1300d` and `fuji_x_h1`. Override from the
environment of the *client* process:

- `VCAM_USB_MODEL` - single model name (e.g. `canon_1300d`, `nikon_d7500`,
  `sony_a7m4`, `fuji_x_h1`)
- `VCAM_USB_ARGS` - extra vcam flags, space separated (e.g. `--fs /path/to/card`)

Note the Fuji models need `--usb` (card reader transport) for the gphoto2
flows below; without a transport flag they set up their wireless personality
in the client process instead (the shim's built-in default uses `--rawconv`
for its raw-converter workflow, which serves a minimal object store).

## Continuous integration

`.github/workflows/ci.yml` builds vcam and runs every model (all Canon,
Nikon, Sony and Fuji tags) against the **distro gphoto2 packages**
(ubuntu-24.04: libgphoto2 2.5.31 / gphoto2 2.5.28) through
`scripts/run-all-regression-tests.sh`:

```sh
sudo apt install -y gphoto2 libgphoto2-dev libusb-1.0-0-dev libexif-dev
cc -o /tmp/gp_client scripts/gp_client.c -lgphoto2 -lgphoto2_port
GP_INSTALL=/usr GP_CLIENT=/tmp/gp_client GPHOTO2_CLI=/usr/bin/gphoto2 \
	SHIM=$PWD/build/libusb-vcam.so bash scripts/run-all-regression-tests.sh
```

Version notes for the system libgphoto2 (2.5.31 vs master):

- Sony `SDIO_GetExtDeviceInfo` is sent with one parameter instead of two -
  accepted by the emulator (real bodies tolerate both).
- Sony shutter speed writes use the mode-2 stepping path (`0x9207` with u8
  steps whose widths are positions in gphoto2's `sony_shuttertable`); the
  emulator therefore registers `0xD20D` as an enumeration in exactly that
  table order so the steps converge. Master uses direct `0x9205` writes and
  is unaffected by the form.
- The Sony gphoto2 flows validated against 2.5.31 pass identically on
  master; the reverse is not guaranteed for features newer than 2.5.31.

## Building libgphoto2 (reference client)

libgphoto2 is not vendored in this repo. Clone it to a scratch dir and build
with meson (no autotools needed):

```sh
git clone --depth 1 https://github.com/gphoto/libgphoto2 /tmp/libgphoto2
meson setup /tmp/gpbuild /tmp/libgphoto2 \
	-Dcamlibs=ptp2 -Diolibs=libusb1,ptpip \
	-Ddocs=false -Ddocs-internal=false -Dudevscriptdir= \
	--prefix /tmp/gp-install
ninja -C /tmp/gpbuild && ninja -C /tmp/gpbuild install
```

On systems without libltdl, a minimal shim over dlopen is enough (used for
loading port/camlib modules):

```sh
# ltdl.h + ltdl.c implementing lt_dlinit/lt_dlopenext/lt_dlsym/lt_dlforeachfile...
cc -shared -fPIC ltdl.c -o /usr/local/lib/libltdl.so
cp ltdl.h /usr/local/include/ && ldconfig
```

## Building and running the test client

`scripts/gp_client.c` is a small libgphoto2 client (autodetect, summary,
config, list, preview, capture, download) used for regression testing. The
`gphoto2` CLI itself can also be used - see below.

```sh
cc -o /tmp/gp_client scripts/gp_client.c \
	-I/tmp/gp-install/include -L/tmp/gp-install/lib/x86_64-linux-gnu \
	-lgphoto2 -lgphoto2_port -Wl,-rpath,/tmp/gp-install/lib/x86_64-linux-gnu

# run against the shim
LD_PRELOAD=build/libusb-vcam.so /tmp/gp_client summary
LD_PRELOAD=build/libusb-vcam.so /tmp/gp_client config
LD_PRELOAD=build/libusb-vcam.so /tmp/gp_client list
LD_PRELOAD=build/libusb-vcam.so /tmp/gp_client preview
LD_PRELOAD=build/libusb-vcam.so /tmp/gp_client download2
```

## Building the real gphoto2 CLI

The CLI needs popt (and optionally readline/nls). On systems without them:

```sh
# popt builds as a static lib without autotools (config.h tweaks only)
git clone --depth 1 --branch popt-1.19-release https://github.com/rpm-software-management/popt
cd popt && cc -O2 -fPIC -DHAVE_CONFIG_H -I. -Isrc -c src/*.c && ar rcs libpopt.a *.o
# config.h needs: _GNU_SOURCE, HAVE_STPCPY/HAVE_SECURE_GETENV/... (glibc has all),
# PACKAGE/VERSION/POPT_SYSCONFDIR/POPT_LOCALEDIR

# gphoto2 CLI from a release tarball (ships ./configure)
PKG_CONFIG_PATH=/tmp/gp-install/lib/x86_64-linux-gnu/pkgconfig:/tmp/popt/lib/pkgconfig \
./configure --disable-nls --without-readline --without-aalib --without-libgd \
	CPPFLAGS="-I/tmp/popt-install/include" \
	LDFLAGS="-L/tmp/popt-install/lib -Wl,-rpath,/tmp/gp-install/lib/x86_64-linux-gnu"
make && make install
```

Run the real CLI against the shim (e.g. 90D):

```sh
LD_PRELOAD=build/libusb-vcam.so VCAM_USB_MODEL=canon_90d \
	gphoto2 --auto-detect
LD_PRELOAD=build/libusb-vcam.so VCAM_USB_MODEL=canon_90d \
	gphoto2 --force-overwrite --set-config capturetarget=1 --capture-image-and-download
LD_PRELOAD=build/libusb-vcam.so VCAM_USB_MODEL=canon_90d \
	gphoto2 --trigger-capture --wait-event-and-download=FILE
```

Or run everything at once:

```sh
scripts/regression-canon-gp.sh [model]
```

## Known limitations

- `download2` runs two captures in one session: gphoto2 switches
  `CaptureDestination` to SDRAM (0x4) from the second trigger onwards, so
  `download` tests the card path and `download2` the SDRAM path
  (partial-object download + TransferComplete).
- The EOS GetEvent terminator is 8 bytes (`{8, 0}`), matching real cameras.
  Do not use a 12-byte terminator (clients log "ran over supplied data") and
  never return a response-only packet for GetEvent: gphoto2's EOS event cache
  double-frees on that.
- The bulk-in splitter in `src/usbthing.c` keeps per-connection state in a
  static, so only one camera is safe to talk to concurrently per process.
- Registering EOS device properties is restricted to u32-typed props
  (`canon_register_capture_props` in `props.c`): gphoto2 hardcodes the
  expected data type per property code in its EOS event unpacker, so
  string/binary props would be misparsed. The full per-model prop dump
  (`vcam_canon_setup`) is currently not wired up and needs rework by the
  dump generator (Phase 3).
